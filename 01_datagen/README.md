# 模块 ① · 虚拟数据库

每天生成一组**自洽**的游戏运营数据，模拟真实游戏生态。这是整个闭环的数据地基——后面三个模块全部建立在这个库上。

---

## 文件

| 文件 | 作用 |
|---|---|
| `schema.sql` | 库结构。含一张 DAU 一致性触发器与一张一致性巡检视图；留存宽表的列按配置在运行时动态生成，故不写在本文件 |
| `config.json` | 全部生成规则：区间、档位、留存曲线与波动、剧本、KPI 目标 |
| `generator.py` | 生成器。含留存模型 `RetentionModel`（基准曲线 + 剧本系数 + 有界平滑波动）与动态视图构建 |

---

## 字段对应关系

### 模块A · 大盘数据 → `daily_metrics`

| 字段 | 列名 | 生成规则 |
|---|---|---|
| 字段1 日期 | `date` | 起点固定 `2026-10-13`，每日 +1 天 |
| 字段2 每日新增用户数 | `new_users` | **区间内随机** 300~1000 |
| 字段3 每日活跃用户数 | `dau` | **不随机**，= `stock_active` + `new_users` |
| 字段4 每日付费率 | `pay_rate` | **区间内随机** 7%~13% |
| 字段5 每日流水 | `revenue` | **不随机**，由付费分层汇总得出 |

### 模块B · 付费分层数据 → `revenue_tiers`

| 字段 | 说明 |
|---|---|
| 字段2 付费用户数 | `pay_users` = DAU × 付费率，落到 `daily_metrics` |
| 字段3~12 | 5 个档位 × (付费用户数, ARPPU)，每档一行 |

档位：`0-10元` / `11-50元` / `51-200元` / `201-2000元` / `2000+元`。

> 档位数量不写死。往 `config.json` 的 `module_b.tiers` 数组里加一项就能增加档位，表结构无需改动。

### 模块C · 留存数据 → `retention_cohorts` + `v_retention_wide`

| 字段 | 列名 | 生成规则 |
|---|---|---|
| 字段1 日期 | `cohort_date` | 新增队列日 |
| 字段2~31 | `d1` ~ `d30` | **D1~D30 留存率**，基准曲线 次留≈45% → 30留≈10% |

```
队列日期       新增      D1      D3      D7     D14     D30
2026-10-13     478  45.47%  28.02%  19.22%  14.09%   9.78%   ← 事件前
2026-12-11     927  36.53%  16.92%   8.94%   6.43%   4.79%   ← 事件后
```

两条设计取舍：

- **存用长表、看用宽表。** `retention_cohorts` 里留存天数是「行」不是「列」，补 D60/D90 只是多几行数据；
  `v_retention_wide` 负责转成 D1~D30 的宽表形态。**宽表的列由 `config.json` 的 `cohort_days` 动态生成**，
  改这个数，表里的行和视图里的列会一起扩展 —— 字段清单不用写进 SQL。
- **未成熟不写 0。** `day_n` 的观测值只在 `cohort_date + day_n` 那天落库，未成熟存 `NULL`。
  未成熟 ≠ 流失为零，这是手抄日报最容易错的地方。

## DAU 的推导模型

规则要求 DAU 不随机、由新增和留存算出来。所以「非新增活跃用户数」才是这个模型的核心：

```
非新增活跃(t) = Σ  各历史日新增(c) × 该批用户在当日的留存率 r(t − c)
              c<t
              + 初始存量 × 存活衰减
```

- 留存率 `r(k)` 来自**模块C 的同一条曲线**（含 ±3% 日波动），所以模块C 是模块A 的上游，两者可互相复算。
- 锚点之间做**对数插值**（插值结果本身即标准幂律衰减），超出最大锚点后按 `tail_decay` 几何衰减。
  为覆盖 D31 以上的长寿队列，尾部衰减系数按「D30=10% → D90≈4~5%」的行业形态取值。
- **首日非新增活跃 = 1000**（配置指定）。实现方式是把初始存量等价成一个「虚拟队列」（注册于起点前一天），使其在第一天恰好贡献 1000。
- 这条链条决定了整个数据形态：留存曲线一改，DAU 与流水的长期走势跟着改。

## 留存的波动模型

要求「每日留存以误差不超过 3% 上下波动」。这里的实现不是「取随机数再截断」，而是**若干条不同周期的正弦按权重叠加**：

```
noise(t, n) = band × Σ wᵢ·sin(2π·t/pᵢ + φᵢ + dᵢ·n) / Σ|wᵢ|
```

- **构造性有界**：|Σ wᵢ·sin| ≤ Σ|wᵢ|，所以 `|noise| ≤ band` 是数学保证，不需要事后截断 ——
  因此不会像截断随机数那样在边界堆积、也不会破坏曲线形态。
- **天然平滑**：t 是队列日期序号、n 是留存天数，相位随 n 缓慢漂移，相邻队列与相邻天数的扰动高度相关，
  「留存随天数递减」的形态得以保持（实测逆序对 0 个）。
- 实测：遍历 90 个队列日 × D1/D2/D7/D14/D30，最大偏离 **2.93%~2.98%**，全部落在 ±3% 内。
- `mode` 可切换：`relative`（±3%，默认）或 `absolute`（±3 个百分点）。

## 四条硬约束（自动校验）

1. **DAU ≡ 非新增活跃 + 新增**
   由数据库**触发器**强制，写入违反直接报错。
2. **各档付费用户数之和 ≡ 付费用户数**
   用「最大余数法」取整分配，不做四舍五入——保证精确相等。
3. **各档流水之和 ≡ 日流水**
   日流水不独立生成，只做汇总。生成后用视图 `v_consistency` 巡检，有异常会报出天数。
4. **留存单调递减 且 日波动 ≤ 配置上限**
   同一队列内保证 r(n) ≥ r(n+1)；生成后逐条比对基准值，越界会告警。

当前巡检结果：**0 天异常**、留存波动 **未越界**。

## 其他设计

- **区间严格不越界。** 周末效应实现为「取区间上半段」而不是乘到区间外，所以新增永远落在 300~1000、付费率永远落在 7%~13%。
- **区间内均值回复。** 指标不会每天完全独立重随机，而是带惯性地游走，更贴近真实运营的连续性；边界用反射处理，避免取值在端点上堆积。把 `mean_revert` 设为 0 即退回每日独立随机。
- **ARPPU = 基准值 × 小幅日波动**，截断在档位区间内。避免某档人均每天翻几倍。
- **历史不可变。** 已生成的日期不会被改写，重复执行自动跳过，只补缺失的天数。
- **可复现。** 随机种子按「种子 + 用途 + 日期」派生，任意一天的数据任何时候重跑都一致。
- **留存队列按观测时点落库。** `day_n` 的留存值在 `cohort_date + day_n` 那天才写入，未成熟的不写（而不是写 0）。

## 剧本（可选层）

纯随机数据没有趋势，看板会变成噪声、活动也失去可归因的对象。所以内置了一个可关闭的剧本层，**只影响留存曲线与付费结构分布，不改动已声明的随机区间**。

| 第几天 | 日期 | 事件 | 影响 |
|---|---|---|---|
| 40 | 2026-11-21 | 版本更新引发首周体验恶化 | 各档留存 ×0.46~0.80（D7 −54%） |
| 60 | 2026-12-11 | 头部用户流失 | L5 少 2 人，当日流水受冲击 |
| 75 | 2026-12-31 | 头部集中度持续上升 | 中小档权重下调，L4/L5 上调 |

**三个开关：**

| 配置 | 作用 |
|---|---|
| `story.enabled = false` | 关掉整个剧本，退回纯随机模式 |
| `story.affects_retention = false` | 留存**严格锁在 45% / 10%** 基准上，只保留 ±3% 日波动；剧本只影响付费结构 |
| 改 `EV-01.impact.retention_mult` | 调节「增长停滞」的幅度，全部填 1.0 等于不留存影响 |

> **区分两件事**：`±3%` 约束的是**日间波动**；剧本事件造成的是**结构性下移**（一次版本更新让 D7 从 19% 掉到 8.7%）。
> 前者由数学构造保证，后者是刻意注入的剧情。如果你要留存水平永远不动，把 `affects_retention` 设为 `false` 即可。

**剧本事件在首次运行时固化成绝对日期落库**，之后增量生成复用——否则每天增量跑，剧情位置会随日期推移而漂移。

## 当前数据概况（90 天）

```
                  新增        非新增活跃        DAU          日流水
冷启动 10-13~11-20  300~1000   1,000→3,960   3,185(均)    ¥22,745(均)
断崖后 11-21~12-20    同上     峰值 4,283@11-18  4,688(均)   ¥34,940(均)
尾部   12-21~01-10    同上     3,878(均)↓      4,689(均)   ¥35,017(均)
```

关键事实：

- **七留：19.0% → 8.9%**（版本更新后腰斩，−54%）
- **非新增活跃池在 11-18 见顶 4,283 后转跌**，末日 4,022；DAU 横盘在 4,700 左右（冷启动→断崖 +47%，断崖→尾部 **0%**）
- **收入结构头部化**：L4(201-2000元) + L5(2000+元) 合计贡献约 **70%** 流水，而人数占比不足 5%
- **目标差距**：末日 DAU 5,524 / 目标 8,000 = 69%；日流水 ¥44,292 / ¥66,667 = 66%

这组数据同时暴露了**三层问题**——留存地基漏水、活跃增长熄火、变现结构高度头部化，正好用来演示"先修地基再谈转化"的诊断顺序。

## 用法

```bash
# 首次：从起点连续生成 90 天
python 01_datagen/generator.py --days 90

# 日常：增量补到最新（已是最新则自动跳过）
python 01_datagen/generator.py

# 清库重建
python 01_datagen/generator.py --reset --days 90
```

Windows 下直接双击项目根目录的 `start.bat`。

> 起点固定为 `2026-10-13`，所以生成超过今天的天数属于**推演数据**（脚本会明确提示），用于预览长期趋势。日常增量运行时每天只追加一天。

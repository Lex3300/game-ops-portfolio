# 模块 ① · 虚拟数据库

每天生成一套**自洽**的游戏运营数据，模拟真实游戏生态。这是整个闭环的数据地基——后面三个模块全部建立在这个库上。

---

## 文件

| 文件 | 作用 |
|---|---|
| `schema.sql` | 库结构：3 张事实表 + 2 张活动表 + 2 张元数据表 + 3 个派生视图 |
| `config.json` | 剧本与基线配置。换游戏、换量级、换剧情都改这里，不用碰代码 |
| `generator.py` | 生成器：三层模型驱动，支持增量续跑 |

---

## 数据模型

```
daily_metrics          日粒度指标（新增 / DAU / 回流 / 付费用户 / 流水 / 时长）
retention_cohorts      留存队列（三留~九十留，未成熟记 NULL）
revenue_tiers          付费分层（非R / 小R / 中R / 大R 的人数与流水）
      ↓ 派生
v_daily_kpi            付费率 / ARPPU / ARPU
v_tier_daily           各层人数占比 / 流水占比 / 分层 ARPU
v_retention_pivot      留存宽表（按队列横排 d1~d90）

activities             活动（模块③产出）
activity_effects       活动效果回流（活动到底有没有用）
story_events           剧本事件（看板用来标注曲线拐点）
sim_config             模拟参数留档 + 运行状态快照
```

---

## 三层生成模型

| 层 | 作用 | 实现 |
|---|---|---|
| **基线** | 正常运营曲线，带周末效应与自然衰减 | `baseline` 配置 |
| **拐点** | 预设剧情事件，制造真实的问题现场 | `story_events`，按「距结束 N 天」定位 |
| **干预** | 活动改写参数，后续数据分布随之变化 | 模块③ 写入 `activity_effects` |

**剧本事件固化为绝对日期落库**，所以之后每天增量生成时，剧情位置不会随日期推移而漂移。

---

## 三条硬约束

1. **自洽**：同一天各分层人数之和 = DAU，各分层流水之和 = 日流水。生成后自动校验，不一致会报错。做法是「先定大R/中R，小R取差额」，避免四舍五入累积误差。
2. **队列成熟度**：`cohort_date + day_n > 最后一天` 时存 `NULL` 而不是 `0`。这是手工抄日报最容易抄错的地方——未成熟不等于流失为零。
3. **可复现**：随机种子按「种子 + 日期」派生，任意一天的数据在任何时候重跑都完全一致。

---

## 用法

```bash
# 首次：补齐 180 天历史
python generator.py --days 180

# 日常：增量补到昨天（已是最新则自动跳过）
python generator.py

# 清库重建
python generator.py --reset

# 指定结束日期（用于回放历史片段）
python generator.py --end-date 2026-10-10
```

Windows 下直接双击项目根目录的 `start.bat` 即可。

## 当前剧本（星海纪元 · 卡牌 RPG）

一个正在恶化的游戏现场，供后续模块诊断与干预：

| 时间 | 事件 | 影响 |
|---|---|---|
| 第 110 天 | 版本更新引发七留断崖 | 七留 ×0.64，日流失率 ×1.30 |
| 第 146 天 | 核心大R用户流失 | 当日流水 −7.5%，大R 少 1 人 |
| 第 162 天 | 头部依赖持续加剧 | 头部集中度 +6%，付费率 ×0.94 |

**结果**：DAU 由 10,726 降至 8,529（**−20.5%**），日流水由 12,809 降至 9,805（**−23.5%**），七留由 14.83% 降至 9.46%，大R 流水占比由 46% 升至 74.6%。

这组数据同时暴露了三个层次的问题——**地基漏水（留存）、活跃衰退（DAU）、变现结构畸形（大R依赖）**，正好用来演示"先修地基再谈转化"的诊断顺序。

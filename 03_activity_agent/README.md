# 模块③ · 活动 Agent（排期引擎 + 配置工作台）

[← 返回作品集首页](../README.md)

两件事：

1. **排期引擎** —— 把「诊断 → 归因 → 选牌 → 排期」从人工判断变成可复现的代码：
   输入当期诊断数据，按活动运营的硬规则算出应排活动，与排期台账比对后只对「未上线」的排期做增改。
2. **配置工作台** —— 把缺口翻译成**可执行的配置建议**（改哪个活动、哪个字段、旧值→新值），
   经看板区块04 走「建议 → Excel → 人工核验 → 发布 → 提交」的闭环落地。

## 配置工作台：一条链路看懂

```
suggestions.json（引擎按诊断生成建议）
    │  看板「一键配置」
    ▼
data/export/config/ACT-XXX.xlsx   ← 27 个活动各一个文件（唯一中间载体，人工核验就改这里）
    │  看板「一键发布」
    ▼
arsenal_seed.json（真源）→ game.db 的 27 张 cfg_act_xxx 表
                        → config_tables.sql（DDL + INSERT，配置即代码）
                        → config_change_log（谁改的 / 旧值 → 新值 / 来源）
```

- 不管是建议带入的改动，还是**人工直接改 Excel**，发布读的都是同一批 xlsx，一套逻辑
- 已上线（有冻结期）的活动不出配置建议，发布时跳过 —— 延续「已定档不动」
- 发布前先校验（活动存在 / 字段合法 / 类型可解析），任一项不过就整批不落库
- 浏览器不能写盘，所以看板由 `dashboard.bat` 从 `http://127.0.0.1:8765` 打开（`serve.py` 本地桥）；
  双击 `index.html` 只能查看，按钮置灰

## 文件

| 文件 | 作用 |
|---|---|
| `schema_activity.sql` | 活动库表结构（全部 IF NOT EXISTS，可反复执行） |
| `arsenal_seed.json` | 活动库种子：7 大类型 / 27 个活动形式 + 各自配置参数（**配置的唯一真源**） |
| `activity_engine.py` | 引擎本体：建表灌库 → 诊断 → 排期规则 → 冻结比对 → 生成建议 → 说明文档 |
| `config_io.py` | 配置工作台核心：Excel 生成/读写、应用建议、发布（种子→库→SQL→流水） |
| `config_tables.sql` | 27 张配置表的 **DDL + 当前配置值**（引擎生成，配置即代码，可 diff/回滚） |
| `排期说明.md` | 自动生成的排期依据文档（每次运行覆盖更新） |
| `活动库总表.md` | 自动生成的活动库总表 + 按类型的配置一览（横向对比用） |
| `../01_datagen/suggestions.json` | 引擎产出的配置建议（看板区块04 读这个） |
| `../02_dashboard/serve.py` | 本地桥服务：给看板提供写 Excel / 发布 / git 命令接口 |

`config_io.py` 也可以单独跑：

```
python config_io.py init            生成 27 个 Excel（已存在不覆盖；--force 强制重建）
python config_io.py apply           把建议写进 Excel（--ids SUG-01,SUG-03 指定条目）
python config_io.py check           只校验，列出待发布变更
python config_io.py publish         校验 + 发布
python config_io.py git             打印建议的提交命令
```

## 数据表（落在 data/game.db）

| 表 | 说明 |
|---|---|
| `activity_master` | **活动库总表**，主键 `activity_id`，一行一个活动形式（名称/类型/人群/默认时长/难度/风险/杠杆），`config_table` 指向该活动自己的配置表 |
| `cfg_act_xxx`（27 张） | **活动配置表，一活动一张**：表名 = `cfg_` + `activity_id` 小写、`-` 换 `_`（`ACT-GIFT-001` → `cfg_act_gift_001`）。表内只有一行，`activity_id` 是固定值；列按活动类型给，同类型字段一致便于横向对比 |
| `activity_schedule` | 排期表：`activity_id` 是外键，一个活动可排多期，因此用 `schedule_id`（排期实例）做主键 |
| `activity_change_log` | 排期变更流水：每次运行记录 add / update / keep，配合 `frozen` 自证「已定档未被动过」 |
| `config_change_log` | 配置变更流水：每次发布记录活动 / 字段 / 旧值→新值 / 来源（建议或人工）/ 批次号 |
| `v_activity_schedule` | 排期联表视图，看板与报表都读这个 |

**为什么一活动一表**：7 大类型的参数集差异很大（抽奖要保底次数、排行榜要排行指标、
限时收益要倍率）。挤在一张宽表里会有一半列长期为空，读一个活动的配置得横向扫过无关字段，
改配置也容易误伤别的活动。拆开后打开表就是该活动的全部参数。

活动 ID（`ACT-GIFT-001`）≠ 排期 ID（`SCH-202610-014`）：主数据与实例数据分离，
同一个「周末限时收益 UP」一个月可以排第 1、2、3 期。

## 排期规则（写死在引擎里）

| 规则 | 逻辑 |
|---|---|
| `R-BASE-01` 常驻基线 | 签到 / 月卡 / 通行证 / 每日礼包 / 新手链 / 回归礼包等全月常驻；商城类不占活动坑位 |
| `R-WEEKEND-01` 周末档 | 未来每个周六日自动排「限时收益 UP」，风险极低的日活工具 |
| `R-STRUCT-01` 结构缺口 | 结构缺口占日均缺口 ≥10%（付费活动相关主导）→ 排 7 天大 R 向定向抽奖 |
| `R-CATCH-01` 承接 | 冲刺活动结束后次日接累充任务，避免活动后流水断崖 |
| `R-LIMIT-01` 稀缺性 | L5 客单达成 <90% → 终身限量礼包补付费跃迁；同活动当月只排一期 |
| `R-OPEN-01` 开服冲榜 | 新服首周荣誉型排行榜，非消费榜 |

## 配置建议规则（同样写死、可解释）

| 规则 | 触发条件 | 动作 |
|---|---|---|
| `C-WHALE-01` | L5 客单达成 < 80% | 终身限量礼包补 328 档 + 库存 3000→2000 |
| `C-BUNDLE-01` | L5 客单达成 < 80% | 累充任务顶档上探 1288，限购 5→6 |
| `C-PITY-01` | 结构缺口占比 ≥ 10% | 保底抽奖 50→45 抽，奖励说明补进度可视化 |
| `C-SCARCITY-01` | 结构缺口 ≥10% 且 L5 < 80% | 存量抽奖提价 + 库存 5000→3000 |
| `C-BREADTH-01` | 流量/转化缺口 > 0 | 低档礼包补 1 元档拉付费率 |

没触发的规则也会列在看板「未入建议」区，判定过程透明；建议落地（发布）后自动消失。

**冻结铁律**：`start_date <= 今天` 的排期自动 `frozen=1`，之后任何一次运行都不会改动它；
引擎只做「新增」和「对未上线活动的调整」，不删除。变更全部落 `activity_change_log` 可审计。

## 与其他模块的关系

- 诊断口径与**区块01/02 完全同源**（同一套公式，Python 侧复刻），排期与建议跟着数据走
- 产出 `01_datagen/schedule.json`（区块03 排期）与 `01_datagen/suggestions.json`（区块04 建议）
- `dashboard.bat` 双击 = 排期引擎 → 看板数据重建 → 本地服务 → 打开页面，一条链跑完

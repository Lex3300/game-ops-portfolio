# 游戏运营数据闭环系统

> 一套**可运行**的游戏运营数据体系：数据生成 → 看板诊断 → 活动干预 → 效果回流，四个环节在同一个数据库上闭环。
>
> 本项目为个人作品集，用于展示数据驱动运营的完整方法论与工程落地能力。所有数据均为程序模拟生成，不含任何真实业务数据。

---

## 一句话说明

大多数游戏运营的日常工作被切成四段：看数据、找问题、上活动、看效果。这个项目把这四段**串成了一条自动化闭环**——每天自动生成数据、自动诊断缺口、自动给出活动建议，并把活动的效果真实写回数据，形成可验证的因果链。

---

## 为什么是"闭环"而不是"五个工具"

单个工具只能证明"我会用某个东西"；闭环能证明"我能把一件事从数据跑到决策再跑回数据"。这四段的关系是：

```
        ① 数据生成
             │
             ▼
        ② 看板诊断 ──→ 发现缺口
             │
             ▼
        ③ 活动干预 ──→ 针对性补缺口
             │
             ▼
        ④ 效果回流 ──→ 改写后续数据分布
             │
             └──────────→ 回到 ①
```

其中 **④ 效果回流**是这个项目最关键的设计：活动不是写在文档里的一句建议，而是真的会改变后续的数据分布，在看板上能看到拐点。**能被验证的干预才算干预。**

## 五个模块

| # | 模块 | 目录 | 作用 |
|---|---|---|---|
| 1 | 虚拟数据库 | `01_datagen/` | 每日生成玩家行为数据，模拟真实游戏生态，可展示、可存储、可调用 |
| 2 | 数据看板 | `02_dashboard/` | HTML 看板，输出多维指标展示与趋势分析 |
| 3 | 活动 Agent | `03_activity_agent/` | 按活动框架产出每日活动计划，并对数据库数据产生正向影响 |
| 4 | 活动知识库 | `04_knowledge/` | 运营活动知识库与诊断技能，趋势分析发现缺口时给出活动建议 |
| 5 | 客服 RAG | `05_cs_rag/` | 客服聊天机器人 + 游戏知识库检索，精准回复玩家问题 |

## 核心设计：数据必须有"剧本"

如果数据是纯随机生成的，会出两个致命问题：看板上的曲线全是噪声、看不出趋势；活动没有任何可归因的对象，"产生了正向影响"无法被验证。

因此数据生成器内置**剧本参数**，分成三层：

| 层 | 作用 | 例子 |
|---|---|---|
| **基线** | 正常的日活/留存/付费衰减曲线，带周末效应与版本周期 | 工作日 DAU 略低，周末回升 |
| **拐点** | 预设的剧情事件，制造真实的问题现场 | 第 30 天起七留下滑 40% |
| **干预** | 活动上线后改写参数，后续数据分布随之变化 | 上礼包链后七留回升，D7 后 DAU 抬升 |

这一层设计让看板上的**每一根曲线都有解释**，也让每一次活动干预都能被回溯验证。

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 数据存储 | SQLite | 单文件、零部署、可直接查看与导出 |
| 数据生成 | Python | 带剧本参数的日粒度模拟引擎 |
| 数据看板 | HTML + ECharts | 静态页面，数据以 JSON 注入，无需后端 |
| 分析诊断 | Python + 技能化知识库 | 收入漏斗分解 + 症状-病因-处方矩阵 |
| Agent | 对话式 Agent | 活动计划生成、客服问答 |

**为什么选 SQLite**：单文件便于随项目分发，可直接用任意工具打开检查，对"展示"这个目标而言比 MySQL/PostgreSQL 更合适。

## 快速开始

```bash
# 首次运行：从固定起点连续生成 90 天数据
start.bat --days 90

# 日常：增量追加（已是最新则自动跳过）
start.bat
```

> 数据库不在仓库里，首次运行会自动生成，克隆后可直接复现。
> 数据起点固定为 `2026-10-13`，之后逐日累积；已生成的日期不会被改写。

## 数据在哪、怎么取

所有数据只落在**一个文件**里：`data/game.db`（SQLite 单文件库）。三种取法：

**① 双击 `export.bat`（最省事）**

导出到 `data/export/`：

| 产物 | 说明 |
|---|---|
| `游戏运营数据.xlsx` | 7 个工作表汇总，比率列自动按百分比显示，首行冻结 |
| `CSV/*.csv` | 每个数据源一个文件，UTF-8 带 BOM，Excel 双击不乱码 |

> CSV 里存的是原始值（如 `0.083524`），Excel 里已设成百分比显示（`8.35%`）。

**② 用任意 SQLite 客户端打开** `data/game.db`
（DB Browser for SQLite / Navicat / DBeaver 均可，无需安装任何东西即可浏览）

**③ 命令行查询**

```bash
python 01_datagen/export_data.py          # 导出 CSV + Excel
python 01_datagen/export_data.py --list   # 看看能导出哪些数据源
```

推荐直接查**视图**（已经算好派生指标，不用自己拼）：

| 视图 / 表 | 内容 |
|---|---|
| `v_daily_kpi` | 日粒度大盘：新增 / 非新增活跃 / DAU / 付费率 / 付费用户 / 流水 / ARPU / ARPPU |
| `v_tier_daily` | 各付费档位：用户数 / 人数占比 / 人均付费 / 流水 / 流水占比 |
| `v_retention_wide` | 每个新增队列的 D1~D30 留存率 |
| `retention_cohorts` | 留存长表（队列日期 × 天数），宽表由它派生 |
| `v_consistency` | 一致性巡检——查出任何一行都说明数据有问题，正常应为 0 行 |

## 设计取舍

**为什么不接真实数据源？** 作品集需要可复现。真实数据受保密约束无法展示，而模拟数据只要有明确的生成规则和剧本参数，同样能完整演示一套分析方法论——**方法论的通用性不依赖数据来源**。

**为什么活动 Agent 也要做？** 只会看数据的人停在"发现问题"，能给出并验证解决方案的人才是运营。活动与数据的因果链是这个项目的核心主张。

**为什么看板不做成动态服务？** 看板的目标是清晰传达信息。静态页面加载快、不依赖后端存活，在演示场景下比动态服务更可靠。
